# Establish the Provider-Neutral Inference Economy Owner Split

- Decision ID: AOA-CENTER-D-0040

## Status

Accepted.

## Index Metadata

- Original date: 2026-08-26
- Surface classes: program direction, federation contract, owner split, decision record
- Center facets: owner descent, inference economy, runtime readiness
- Mechanic parents: none
- Guard families: owner boundary, sibling-owner boundary, baseline gate, release and acceptance separation
- Posture: accepted program direction; implementation, admission, pilot, proof, and acceptance remain owner-local

## Context

The provider-neutral execution-economy program spans Codex, API, and local-model
routes. Its required evidence crosses runtime observations, typed control-plane
requirements, session continuity, model identity, shared measurement grammar,
proof, host admission, and role-bearing handoff. Without an explicit center
split, the constitutional repository could absorb sibling implementation or
mistake a live process, a partial counter, or a green validator for a comparable
baseline or an accepted runtime claim.

## Options considered

1. Put one unified measurement and execution implementation in
   `Agents-of-Abyss` for convenience.
2. Leave each owner to evolve independently without a program-level map or
   common baseline law.
3. Keep the center responsible for program direction, owner boundaries, and
   baseline stop-lines while each specialized owner carries its local contract,
   implementation, evidence, and acceptance route.

## Decision

Choose option 3.

`Agents-of-Abyss` owns the program-level direction, the owner split, the
provider-neutral baseline law, and the federation stop-lines. It does not own
runtime implementation, source-local measurement meaning, role meaning, proof
verdicts, memory truth, host enforcement, or sibling owner acceptance.

The specialized responsibility split is:

| Owner | Owns | Does not own |
|---|---|---|
| `aoa-agents` | role, mandate, identity, and handoff meaning | runtime or inference measurement |
| `aoa-sdk` | typed provider-neutral observation requirements and control-plane seams | runtime execution or proof verdicts |
| `abyss-stack` | raw runtime observation, session/tool lifecycle, and model/tool/queue/end-to-end timing | center doctrine or owner acceptance |
| `aoa-stats` | shared measurement grammar and derived comparisons | source populations, proof, route authority, or acceptance |
| `.aoa` | session-evidence routing, rehydration, graph/index projections, and evidence/context handoff | policy authority, source meaning, proof, or acceptance |
| `aoa-session-memory` | portable session-memory kernel, memory-object lifecycle, and admitted portable exports | session-evidence routing, proof, or acceptance promotion |
| `aoa-models` | provider/model/runtime/tokenizer/billing facts and realization identity | activation authority or owner routing |
| `aoa-evals` | matched fixtures, blind spots, and bounded eval/net-benefit verdicts | runtime execution or source implementation |
| `abyss-machine` | host resource, storage, artifact trust, and admission evidence | federation doctrine or sibling source meaning |

## Baseline sufficiency and acceptance route

The concrete sufficiency owner is the independent `goal-execution-reviewer`
office in the Goal organization. The `d0-baseline` direction master assembles
and binds the candidate but cannot self-accept it. The authoritative review
receipt is `reviewer/cycles/<review-cycle>/review-result.json`, materialized in
`reviewer-state.json`; its `d0-baseline` entry must carry `direction_id`,
`reviewed_at`, `snapshot_digest`, an explicit baseline-sufficiency disposition,
and `evidence_refs` that bind the candidate and both arms. A `baseline-ready.json`
receipt is valid only when it names that exact review receipt and candidate
digest. A missing, stale, unbound, or rework disposition is not acceptance.

The Goal master owns the whole-direction return/closeout and final Goal/owner
acceptance route. It does not replace the independent reviewer's baseline
sufficiency decision. Runtime outcome, eval verdict, closeout, owner
acceptance, and human acceptance continue to require their own receipts.

The baseline gate requires one current governed Codex adapter and one current
existing local-model route to run the same frozen, owner-approved fixture in a
comparable capture window. Each arm must expose, or explicitly mark missing,
input/cached/output tokens, turns and model calls, model-visible tool-schema
bytes/tokens, tool calls and commands, intermediate output, compactions and
observation gaps, attempts/retries/recovery/rework, model/tool/queue/end-to-end
wall time, provider/model/runtime/tool-profile identity, runtime outcome, eval
verdict, closeout, owner acceptance, and human acceptance. A `baseline-ready`
receipt requires independent reviewer sufficiency acceptance.

Default-off source contracts, adapters, tests, and wiring may land before the
baseline. Behavioral activation, live pilot, promotion, and economy claims
must wait for the admitted paired baseline. Codex-specific behavior remains in
the adapter layer and must not enter the provider-neutral ABI.

## Rationale

Option 3 makes the center useful without making it sovereign over specialized
truth. It gives future owners a stable map and a common admission stop-line,
while preserving local implementation and evidence authority. The paired
baseline prevents stale cross-provider comparisons and keeps missingness visible
instead of converting transport or partial runtime counters into economy claims.

## Consequences

- The roadmap can name the program and its owner boundaries without promising
  sibling implementation or runtime readiness.
- Specialized owners can land default-off source slices and retain their local
  validators, receipts, runtime routes, proof, and acceptance semantics.
- Baseline admission remains a separate state from source, CI, deployment,
  runtime outcome, eval verdict, closeout, and owner/human acceptance.
- A missing endpoint, trust/admission verdict, metric, or sufficiency receipt
  remains explicit missingness and blocks promotion rather than becoming zero.
- The residual cost is coordination across several owner routes before the
  first activation or economy comparison is honest.

## Follow-up route

Each specialized owner carries the local contract and implementation slice in
its own repository or owner surface. `abyss-stack`, `abyss-machine`, `.aoa`,
and the measurement, session-memory, model, role, SDK, and eval owners must
provide their own current receipts before the direction emits `baseline-ready`.
The independent Goal reviewer decides baseline sufficiency through the receipt
route above; the Goal master remains the acceptance route for the whole
direction, and no center source landing alone proves runtime, eval, closeout,
or owner/human acceptance.

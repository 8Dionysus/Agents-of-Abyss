# AoA System Design

## Role

`DESIGN.md` describes the system form of Agents of Abyss.

It is not the charter, roadmap, ecosystem map, implementation plan, or agent
instruction file.

It answers one question:

What shape should AoA take as it grows toward OS Abyss?

## Design Thesis

AoA is a federated operating form for long-horizon human+AI work.

It is designed to keep agency powerful without becoming opaque, to keep
knowledge alive without losing source ownership, and to let many specialized
organs mature without collapsing into one repository.

The center names the city.
The organs carry their own work.
The routes keep return possible.

## Design as Appearance

AoA should appear as a navigable polis:

- a clear public front door
- a small number of durable civic surfaces
- visible districts
- named routes
- reviewable claims
- machine companions that help orientation without becoming authority

The system should feel explorable, not buried. Ritual language is allowed when
it clarifies motion. Mythic language is allowed when it strengthens memory.
Neither may replace evidence, ownership, or review.

## Design as Anatomy

AoA is not one monolith.

It is composed of:

- center surfaces
- source-owned repositories
- derived layers
- routing layers
- runtime bodies
- memory surfaces
- proof and evaluation surfaces
- agent-facing lanes
- generated machine companions
- human-readable maps and laws

Each layer may support the others. No layer should silently steal the authority
of another.

## Design as Operation

AoA should operate through routes, not hidden force.

A good operation has:

- an entry surface
- a named owner
- a bounded scope
- an evidence path
- a review path
- a return route
- a clear stop-line

Agency is strongest when it remains inspectable.

## Design as Aim

The long aim is OS Abyss.

OS Abyss is not merely an app, repo, runtime, or dashboard. It is the target
operating condition of the whole system:

a local-first / hybrid human+AI environment where agents, memory, knowledge,
proof, routes, rituals, tools, and runtime bodies can cooperate without
dissolving source truth, human judgment, or reversibility.

AoA is the constitutional and federated path toward that condition.

## Design Principles

### 1. Legibility before power

A stronger system is not one that does more invisibly. A stronger system is one
whose powers can be named, routed, reviewed, and returned from.

### 2. Federation before absorption

The center should clarify the federation. It should not become every organ.

### 3. Source before summary

Summaries, generated capsules, registries, and routing maps may guide. They do
not become source truth.

### 4. Human-readable, machine-usable

A surface should be readable by a human and useful to an agent. When those needs
conflict, split the surface rather than corrupting both.

### 5. Bounded agency

Agents may act.
Agents may route.
Agents may propose.
Agents may validate.

But lasting agency must remain bounded by owner surfaces, review windows,
evidence, rollback, and explicit handoff.

### 6. Ritual becomes workflow

AoA may use symbolic language, quests, cycles, mechanics, and mythic naming.
These are valid when they make recurring work more memorable, bounded, and
repeatable.

They fail when they hide responsibility.

### 7. Generated surfaces are companions

Generated files may compress, index, or orient. They must point back to stronger
authored surfaces. They should be reproducible.

### 8. Growth should sharpen the map

A new repository, layer, mechanic, or route is integrated only when it makes
ownership, reviewability, and return clearer than before.

### 9. Owner-local questions, shared statistical grammar

Each organ owns what is meaningful to measure about its own objects, including
the population, missingness, evidence route, privacy posture, and authority
ceiling. `aoa-stats` owns the shared grammar and cross-owner composition; it
does not take the local question or source meaning away from the owner.

## Good Design Feels Like

A newcomer can find the front door.
An agent can find the nearest rule.
A maintainer can find the owner.
A claim can find its evidence.
A drift can find its reanchor.
A generated surface can find its source.
A future self can find the reason.

## Bad Design Smells Like

- root inflation
- duplicate doctrine
- hidden authority transfer
- generated files cited as source truth
- myth replacing review
- agent autonomy without anchors
- roadmap promises without owner evidence
- runtime language pretending to be live implementation
- center convenience absorbing specialized meaning
